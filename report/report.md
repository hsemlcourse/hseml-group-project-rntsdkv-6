## 1. Введение и постановка задачи

- **Цель проекта:** создать модель, позволяющую предсказывать наиболее подходящих разработчиков для выполнения новой задачи на основе их исторической активности, может быть полезно рукодителю нескольких команд для поручения задачи определенному сотруднику, уже имеющему экспертизу, что в свою очередь позволяет экономить ресурсы
- **Формулировка задачи:** ранжирование разработчиков по их исторической активности
- **Обоснование метрики качества:**
  a. **Recall@5** (основная) – доля задач, где реальный исполнитель попал в топ-5 рекомендаций
    Обоснование:
      - Метрика интуитивно понятна заказчику конечной модели
      - Легко интерпретировать корректность назначенных задач
      - Стандарт в рекомендательных системах
  b. **MRR (Mean Reciprocal Rank)** (дополнительная)
    Обоснование:
      - Учитывает позицию правильного ответа внутри топа
      - Штрафует за низкую позицию релевантного кандидата
      - Дополнение Recall: MRR различает rank
  c. **NDCG@5**
    Обоснование:
      - Можно использовать степень релевантности
      - Нормализация (0..1)

## 3. Обработка и подготовка данных

### 3.1. Очистка данных

**Пропуски:**
Обнаружены в следующих полях:
- `employees.login`: 307 пропусков (2.2%) -> строки удалены
- `jira_issues.issue_desc`: 2 пропуска (<0.01%) -> строки удалены
- `gitlab_commits.author_login`: 87 пропусков (0.09%) -> строки удалены

**Дубликаты:**
- Jira: удалены дубликаты по паре `(assignee_login_nm, issue_rk)` (над одной задачей могут работать несколько разработчиков)
- GitLab: удалены дубликаты по `commit_hash` (уникальный признак)

**Унификация логинов:**
Все логины приведены к нижнему регистру и очищены от пробелов

**Очистка текста:**
Для описаний задач и коммитов применена нормализация:
- Приведение к нижнему регистру
- Удаление спецсимволов (кроме букв и цифр)
- Нормализация пробелов

**Выбросы:**
- `work_experience_day_cnt`: обнаружено 724 высоких выброса (значения > Q3 + 1.5×IQR). Выбросы не удалялись, т.к. могут соответствовать реальным сотрудникам.
- GitLab: удалены коммиты с «мусорными» заголовками: `wip`, `fix`, `upd`, `test`, `tmp`, `merge`, `revert`

### 3.2. Работа с фичами

**Созданные фичи:**

1. **Профили разработчиков** (`build_developer_profiles`):
   - `jira_issues_count` — количество задач Jira, назначенных на сотрудника
   - `commits_count` — количество коммитов в GitLab
   - `jira_text` — объединённое описание всех задач сотрудника
   - `gitlab_text` — объединённые заголовки всех коммитов автора
   - `developer_profile_text` — полный текстовый профиль (Jira + GitLab)
   - `profile_words_count` — количество слов в профиле

2. **Очищенные текстовые поля:**
   - `issue_desc_clean` — нормализованное описание задачи
   - `commit_title_clean` — нормализованный заголовок коммита

**Итоговое количество признаков:**
- Сотрудники: 11 исходных + 6 новых = 17 признаков
- Jira: 6 исходных + 1 новый = 7 признаков
- GitLab: 7 исходных + 1 новый = 8 признаков

### 3.3. Визуализации

В ходе EDA построены:
1. **Pie chart** — распределение сотрудников по должностям (топ-10 + остальные)
2. **Статистика по опыту работы** — min, max, Q1, Q3, IQR, количество выбросов
3. **Распределение по проектам** — краткая статистика по `project_short_nm`

### 3.4. Разделение данных

**Стратегия:**
- Разделение по уникальным `issue_rk` (идентификатор задач)
- Соотношение: **60% train / 20% val / 20% test**
- `random_state=42` для воспроизводимости

**Результат:**
- Train: 59 998 задач (60.0%)
- Val: 20 000 задач (20.0%)
- Test: 20 000 задач (20.0%)

**Предотвращение data leakage:**
- Разделение по `issue_rk` гарантирует, что задачи из одного issue не попадут в разные выборки
- Профили разработчиков строятся на основе всех данных
- При обучении модели используется только train-выборка, validation и test — для оценки качества
